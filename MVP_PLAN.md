# RescueLink — MVP Implementation Plan

## Current State ✅

The following is already built and working:

- **Firebase Auth** — sign up / sign in / sign out with email & password
- **Firestore user profiles** — `users/{uid}` and `operators/{uid}`
- **Customer UI** — map home screen, booking flow, live tracking, job history, vehicles
- **Driver UI** — 6-step onboarding, pending / rejected / approved states, earnings, live job screen
- **Navigation** — role-based routing (customer / operator) and verification status routing
- **Firestore security rules** — owner-only read/write on user and operator documents

---

## Phase 1 — Make the Core Loop Real

> **Goal:** A customer can request a job and a driver can accept it.

### 1.1 — Real file uploads for driver onboarding

Currently `MockUploadedFile` stores only metadata with no actual file. Replace with Firebase Storage.

- Driver takes a photo / picks a file → upload to `gs://rescuelink/operators/{uid}/licence-front.jpg`
- Store the download URL in `operators/{uid}` instead of mock metadata
- **Screens affected:** `OperatorOnboardingScreen` (steps with document uploads)

### 1.2 — Admin driver approval

Currently driven by dev-only buttons (`devApproveOperator` / `devRejectOperator`). For a real flow:

- Use Firebase Console directly to view `operators/` documents and manually change `verificationStatus` to `"approved"` for MVP
- Write a **Cloud Function** triggered on `operators/{uid}` write → when status becomes `"approved"`, send the driver an FCM push notification: *"You're approved! You can now start accepting jobs."*

### 1.3 — Job request → Firestore

When customer taps **"Confirm & start tracking"** in `BookingFlowScreen`, write a document to `jobs/{jobId}`:

```json
{
  "id": "auto-generated",
  "customerId": "user.uid",
  "customerName": "user.firstName",
  "vehicleLabel": "Ford Focus · AB12 CDE",
  "issueLabel": "Flat tyre",
  "canMove": true,
  "pickupLat": 51.5074,
  "pickupLng": -0.1278,
  "dropoffLabel": "Home — E1 6RF",
  "status": "requested",
  "createdAt": "ISO timestamp",
  "totalGbp": 89.00
}
```

- Navigate customer to `LiveTrackingScreen` with the new `jobId`
- `LiveTrackingScreen` subscribes to `jobs/{jobId}` with `onSnapshot` for live status updates

### 1.4 — Driver job feed

`OperatorHomeScreen` currently shows mock data. Replace with a live Firestore query:

- Query `jobs` where `status == "requested"` — for MVP, show all open jobs (add geo-filtering in Phase 2)
- Driver taps **Accept** → write `driverId: uid` and `status: "en_route"` to the job document
- Customer's `onSnapshot` listener picks up the status change automatically

## Phase 2 — Location & Live Tracking

> **Goal:** Customer sees the driver moving on the map in real time.

### 2.1 — Driver broadcasts location

In `OperatorLiveJobScreen`, use `expo-location` to write coordinates to Firestore every 5 seconds:

```json
{
  "currentLat": 51.512,
  "currentLng": -0.119,
  "lastSeen": "ISO timestamp"
}
```

Written to `operators/{uid}` (or embedded on the active `jobs/{jobId}` document).

### 2.2 — Customer receives live location

`LiveTrackingScreen` already has a map. Subscribe to the job / operator document with `onSnapshot` and update the driver pin position as coordinates change.

---

## Phase 3 — Payments

> **Goal:** Customer pays, driver gets paid.

### 3.1 — Stripe payment intent (customer side)

- Install `@stripe/stripe-react-native` in the Expo app
- Create a Cloud Function `createPaymentIntent(jobId)` — called when customer confirms booking, returns a `client_secret`
- Customer app presents the **Stripe Payment Sheet** using the `client_secret`
- On success, update `jobs/{jobId}.paymentStatus = "paid"`

### 3.2 — Stripe Connect payouts (driver side)

- During driver onboarding, replace the mock bank account fields with a **Stripe Connect onboarding link** (generated by a Cloud Function)
- When a job is marked `"completed"`, a Cloud Function triggers:
  1. Charges the customer's saved payment method
  2. Transfers the driver's cut (e.g. 80%) to their Stripe Connect account
  3. Retains the platform fee (e.g. 20%)

---

## Phase 4 — Push Notifications

> **Goal:** Neither side misses a critical event.

| Event | Recipient |
|---|---|
| New job posted nearby | Nearby available drivers |
| Driver accepted the job | Customer |
| Driver is 5 minutes away | Customer |
| Driver has arrived | Customer |
| Job completed | Customer (with receipt) |
| Onboarding approved | Driver |
| Onboarding rejected (with reason) | Driver |

All notifications sent via **Firebase Cloud Messaging (FCM)** triggered from Cloud Functions.

## Project Structure (monorepo)

Keep everything in the same `rescuelink` repository:

```

├── src/                          ← Expo app (existing)
│   ├── firebase/                 ← Firebase service layer (existing)
│   ├── screens/
│   ├── context/
│   └── navigation/
├── functions/                    ← Cloud Functions backend (to be added)

│   │   ├── jobs.ts               ← job matching, status transitions
│   │   ├── payments.ts           ← Stripe webhooks, payouts
│   │   ├── drivers.ts            ← approval notifications
│   │   └── notifications.ts      ← FCM helpers
│   ├── package.json
│   └── tsconfig.json
├── firebase/
│   └── firestore.rules           ← security rules (existing)
├── .env                          ← Firebase config keys (gitignored)
├── .env.example

```

